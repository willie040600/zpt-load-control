# 宅配通 車趟裝載控制塔(示意版)

完整的啟動、操作與演算法說明請見 [使用說明書](使用說明書.md)。

## 本地新增：宅配通車趟成本最佳化（DP＋MILP）

從轉運中心或全台網路點選「演算法比較」，或開啟 `http://127.0.0.1:5173/?view=compare`。
左側可選實際現況或**原專案規則法（改派＋併車）**，右側為**宅配通車趟成本最佳化（DP＋MILP）**的 A–D 情境。
兩個 3D 場景共用中心、日期、時間與播放速度；新方案的車型、車趟數及籠數會實際更新。
比較表列出成本、節省、趟次、貨量、容量利用率與付費載貨 35 噸趟次；群組可搜尋、定位與匯出 CSV。

本專案支援本地執行，程式碼與使用說明書存放於 GitHub；尚未部署為公開網站。原始 Excel 不修改，也不包含司機姓名、車牌與電話於新增前端資料。

### 本地啟動

一般環境先 `npm ci`，再 `npm run dev -- --host 127.0.0.1`。
此工作區已有依賴，可直接執行 `bash start-local.sh`；腳本亦支援 Codex 內建 Node。

### 重跑你的演算法

```bash
python -m pip install -r analysis/requirements.txt
python analysis/optimize_report.py --inputs /path/6月原始資料.xlsx /path/7月原始資料.xlsx
python analysis/algorithm_demo.py
npm run build
```

`optimize_report.py` 產出 `src/data/prompt-comparison.json` 與 `analysis/out/prompt/` 下的四情境完整群組 CSV、容量異常 CSV、資料檢查 JSON、Markdown 摘要及九工作表 Excel 報告。
Excel 使用 Codex 內建 artifact-tool；在一般 Python／Node 環境可加 `--no-excel`，JSON／CSV／摘要與 3D 不受影響。
`algorithm_demo.py` 執行六項邊界測試，並顯示本次資料的 300 群暴力枚舉、DP/MILP 對照、貨量守恆與 35 噸敏感度。
若原始檔的單號與現有 `trips.json` 不一致，先依下方既有更新流程重建原專案資料，再重跑比較模型。

### 模型口徑

- 規格：`analysis/車趟成本最佳化規格.md`；核心：`analysis/prompt_optimizer.py`；集中參數 `PARAMS`。
- 依派車單號取最高整趟費用、加總籠車數；與運費分撥差距達 0.5% 或容量眾數不符時停止計算並輸出檢查。
- A 僅群組內已有車型與承運商報價；B 可用同路線同溫層其他既有車型；C 以 50% 路線中位價與 50% 合格最低價混合單價試算；D 取消時窗、全面低價，為理論上限。
- A–C 依作業日期 × 車次名稱 × 溫層 × 固定兩小時時段分群；免費載貨車保留並可吸收同群需求，付費零籠車的固定成本保留。沒有跨路線／跨溫層套價。
- DP 用標準 35t=20、17/18.5/25t=14 籠覆蓋需求，若比現況貴則保留現況；原始超載紀錄另行揭露，不放大新方案容量。
- 35 噸 MILP 敏感度以全期間付費載貨趟次為上限，含保留現況車的資源消耗；逐群禁止成本增加，避免事後回退造成超過上限。此表獨立於上方無上限 DP 的 3D 情境。
- KPI 使用作業日期；3D 使用實際出發日曆日並保留跨午夜進出。月／年化按實際作業日日均 × 30／365 推估。
- 原專案規則法沿用原本已驗證項目（不含時窗池），模型假設不同；比較頁不套用手動採納狀態，兩方案彼此獨立。
- 新車沿用群組來源的實際出發時刻與行車時間示意，未解中繼順序、個別運單截止時間、逐日車隊可用量或碼頭最佳化，並非 VRP。

目前資料的去重成本 30,312,750 元，與運費分撥一致；逐列重複費用 845,000 元。
A／B／C／D 分別節省 799,650／2,224,750／2,458,350／3,763,350 元。
B 在 35 噸付費載貨趟次限制為現況 1.0 倍時，節省 1,798,750 元。數字均為模型試算，含假設與限制。

以 3D 地圖呈現集貨、轉運、繼送的逐車趟裝載率,並把第 0 步的低裝載歸因與建議動作放進同一個畫面。

## 兩種視角
- **轉運中心視角(預設)**:北轉、桃轉、中轉、高轉四座轉運中心的等角 3D 畫面。南面為發車碼頭、東面為進站碼頭,車趟依真實發車與抵達時間進出,碼頭內側的籠車堆會隨裝卸增減;碼頭全滿時車輛在臨時車位排隊,碼頭空出後再進去。右側面板可採納建議、回填原因代碼,KPI 即時重算。
- **全台網路視角**:原本的台灣地圖,看站所與轉運中心之間的所有路線。

碼頭分配、裝貨 45 分鐘、卸貨 40 分鐘皆為示意(資料沒有碼頭紀錄)。3D 畫面顯示所有實際發車或到著為該中心的車趟,不論由哪個中心結帳;KPI 則依「結帳單位」計算,各中心加總不重複。資料沒有桃轉這個結帳單位,結帳在北轉且發車或到著為桃轉的車趟 KPI 歸桃轉,北轉與桃轉之間的對開車 KPI 算在發車端。

## 資料
- 來源:115 年 6 月、7 月(1–20 日)車趟派遣原始數據,共 9,748 趟(以派車單號去重)。
- `src/data/trips.json`:每趟車的裝載率、費用、歸因代碼與建議動作。不含司機姓名與車牌。
- 日期是**實際出發的日曆日期**,不是原始資料的「作業日期」(繼送常在作業日的隔天凌晨出發,約 47% 的車趟兩者不同)。轉運中心視角的時間軸是連續的:會一併顯示前後一天跨午夜的進出,碼頭占用也接得起來。
- `src/data/meta.json`:資料不完整的日期(例如 7/11 整天沒有資料、6/1 缺前一天的凌晨繼送),下拉選單會標示。
- 空載成本 = 車次費用 ×(1 − 裝載率),只計裝載率 <80% 的車趟。可省金額依同路線中位價估算(只計車次費用 >0 的車趟,0 元車趟約 8%,不是價格),非正式會計口徑。
- 站所座標依運費表地址推估,僅供示意;金門為了畫面集中往東移。

## 建議動作分級
- 已驗證(可立即執行):35 噸載 ≤14 籠且同線常用 17 噸並較便宜 → 改派 17 噸;同站同日時差 ≤30 分 → 合併;跨站同方向時差 ≤30 分 → 共車。
- 時窗調整池:時差 30–120 分,需先把發車時間壓到 30 分內。

## 更新資料(analysis/)
從原始 Excel 重新產生 `src/data/trips.json`:
1. 把 6 月、7 月的「車趟派遣SOP原始數據.xlsx」放到 `analysis/data/jun.xlsx`、`analysis/data/jul.xlsx`。
2. 執行 `sh analysis/run_all.sh`(需要 Python 3、pandas、openpyxl)。腳本會印出並寫出中文,Windows 上已在腳本內強制使用 UTF-8。
3. 再執行 `npm run build`。

各腳本:`prepare.py` 轉檔 → `step0.py` 低裝載歸因 → `mismatch.py` 車型錯配分級 → `export.py` 產生建議動作與 JSON。
